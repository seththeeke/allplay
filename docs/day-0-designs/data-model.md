# Data Model

Status: Day 0 design, 2026-11-17.

This document defines every entity All Play persists, the DynamoDB tables that hold them, the indexes on those tables, and a sample item for each entity. It is the single source of truth for entity names: backend `models/` files and `dao/` folders use the names in this document exactly.

Related specs: `game-engine.md` (game state shape and rules documents), `action-decision.md` (rate limits and the counters it adds), `authn-authz.md` (player identity), `cdk-stacks.md` (table provisioning).

## 1. Storage Principles

1. All persistence is DynamoDB in on-demand (PAY_PER_REQUEST) billing mode. No table has provisioned capacity, so idle cost is zero.
2. One table per entity. Tables are named `AllPlay-<Entity>-<Stage>` where `<Stage>` is `Test` or `Prod`, because both stages share one AWS account.
3. Every table has point-in-time recovery enabled in Prod only, deletion protection enabled in Prod only, and `RemovalPolicy.RETAIN` in both stages.
4. Every item carries `entityVersion` (integer, the schema version of the item shape) and `createdAt` / `updatedAt` (ISO 8601 UTC strings).
5. Enum values are stored in ALL_CAPS (`IN_PROGRESS`, `GUEST`).
6. Identifiers generated by the backend are ULIDs, so they sort by creation time. Identifiers issued by Cognito are stored as issued.
7. Items that expire carry a numeric `ttl` attribute (epoch seconds) and the table's TTL is configured on that attribute.
8. Every read path in the API is a `GetItem` or a `Query`. `Scan` is used only by the daily metrics rollup job (Section 11). Reads of a table's own keys are strongly consistent, so a player always sees their own writes; reads of a global secondary index are eventually consistent, as DynamoDB requires.
9. Optimistic concurrency: entities mutated by concurrent requests carry an integer `version` and every write uses a condition expression on it.
10. Guest retention: every item owned only by a guest (`Player`, `Preference`, `SeatAssignment`, `PlayerStats`, and a `GameSession` whose only seat is a guest's) carries `ttl` = the guest's last activity + 90 days. The ttl moves forward whenever the guest's `lastActiveAt` does (at most once per hour) and whenever the item is written, so an active guest never expires and an abandoned guest's data disappears 90 days after its last visit. Account items never carry `ttl`; a merge copies guest items to the account without it. The Cognito guest identity is not deleted; it costs nothing, and a guest returning after expiry starts fresh.

## 2. Player Identity

A player is anyone who uses All Play, signed in or not. The `playerId` is derived from the caller's Cognito Identity Pool credentials on every API request (`authn-authz.md` Section 4):

| Kind | playerId format | Source |
|---|---|---|
| `GUEST` | `GUEST#<identityId>` | Cognito Identity Pool unauthenticated identity, for example `GUEST#us-east-1:4f1c...` |
| `ACCOUNT` | `ACCT#<sub>` | Cognito User Pool `sub` of the signed-in user |

A guest who signs up or signs in has their data merged into the account player (Section 9) and the guest `Player` item is marked `MERGED`.

## 3. Entity Overview

| Entity | Table | Purpose | Expires |
|---|---|---|---|
| Player | `AllPlay-Players-<Stage>` | One item per guest or account | Guests: 90 days after last activity |
| Preference | `AllPlay-Preferences-<Stage>` | Layered preferences: application scope and per-game scope | Guests: 90 days after last activity |
| GameSession | `AllPlay-GameSessions-<Stage>` | One game being played: rules reference, engine state, status | Guest-only sessions: 90 days after last activity |
| SeatAssignment | `AllPlay-SeatAssignments-<Stage>` | Links a player to a session seat; the social layer | Guests: 90 days after last activity |
| PlayerStats | `AllPlay-PlayerStats-<Stage>` | Win/loss statistics per player, game and variant | Guests: 90 days after last activity |
| MergeToken | `AllPlay-MergeTokens-<Stage>` | Single-use proof that a caller owned a guest identity | 10 minutes |
| RateLimitCounter | `AllPlay-RateLimits-<Stage>` | Per-player request counters for the decision endpoint | 2 days |
| MetricRollup | `AllPlay-MetricRollups-<Stage>` | Daily aggregates shown on /admin | No |
| GameDefinition | `AllPlay-GameDefinitions-<Stage>` | Community rules documents (Game Building phase) | No |

Core game rules documents (Spider Solitaire and every other game built by the All Play team) are not stored in DynamoDB. They are versioned JSON files bundled with the backend (`game-engine.md` Section 3). `GameDefinition` holds only community-built games and is provisioned in the Game Building phase; its key design is fixed here so that the engine's rules repository interface covers both sources from day one.

## 5. Preference

Table `AllPlay-Preferences-<Stage>`. Preferences are layered: the `APP` scope holds application-wide settings, and each `GAME#<gameId>` scope holds settings for one game. The client resolves an effective value by reading the game scope first and falling back to the application scope, then to built-in defaults. One `Query` on the partition returns every layer.

| Key | Attribute | Type |
|---|---|---|
| Partition key | `playerId` | String |
| Sort key | `scope` | String: `APP` or `GAME#<gameId>` |

No GSIs.

Preferences are saved automatically as the player changes them (there is no settings "save" button). A guest's preference items carry `ttl` (Section 1, principle 10), refreshed on every write, and the table's TTL attribute is `ttl`. Writes are `UpdateItem` with `SET` on only the changed fields, so concurrent changes to different fields never overwrite each other.

`APP` scope attributes:

| Attribute | Type | Default | Notes |
|---|---|---|---|
| `zoomLevel` | Number | `1.25` | Range 1.0 to 3.0 in steps of 0.25 |
| `theme` | String | `DEFAULT` | `DEFAULT`, `HIGH_CONTRAST`, `BLACK_AND_WHITE`, `FOUR_COLOR`, `DARK` |
| `voiceOutputEnabled` | Boolean | `false` | Polly speech for prompts, errors and hints |
| `voiceId` | String | `Joanna` | Polly neural voice |
| `speechRate` | Number | `1.0` | Range 0.75 to 1.5 |
| `autoConfirm` | Boolean | `false` | Apply a uniquely matched voice action without confirmation |
| `reducedMotion` | String | `SYSTEM` | `SYSTEM`, `ON`, `OFF` |
| `listenTimeoutMs` | Number | `1200` | Silence after speech that ends listening |
| `appHelpSeen` | Boolean | `false` | First-visit help walkthrough for the portal |

`GAME#<gameId>` scope attributes are generic plus game-specific. Generic attributes:

| Attribute | Type | Notes |
|---|---|---|
| `helpSeen` | Boolean | First-game help walkthrough completed for this game |
| `lastOptions` | Map | The options used for the most recent new game, so "new game" reuses them |
| `overrides` | Map | Any `APP` attribute overridden for this game only, for example a different `zoomLevel` |

## 6. GameSession

Table `AllPlay-GameSessions-<Stage>`. A session is one game from deal to finish. It holds the engine state and nothing about who is playing beyond seat ids; the player link lives in `SeatAssignment` (Section 7). This split is the seam that lets multiplayer sessions exist later without reshaping this table.

| Key | Attribute | Type |
|---|---|---|
| Partition key | `sessionId` | String (ULID) |

No GSIs.

Attributes:

| Attribute | Type | Notes |
|---|---|---|
| `sessionId` | String | ULID |
| `gameId` | String | For example `spider-solitaire` |
| `rulesSource` | String | `CORE` (bundled) or `COMMUNITY` (`GameDefinition` table) |
| `rulesVersion` | Number | Pinned at creation; a session always plays the rules version it started with |
| `engineSchemaVersion` | Number | Version of the engine state format |
| `options` | Map | Resolved game options, for example `{ "suits": 1, "dealStyle": "MICROSOFT" }` |
| `variantKey` | String | Stable string form of the options used for statistics: `suits=1;dealStyle=MICROSOFT` |
| `seats` | List of Map | `[{ "seatId": "S1", "playerId": "..." }]`; Spider Solitaire always has exactly one seat |
| `status` | String | `IN_PROGRESS`, `WON`, `ABANDONED` |
| `version` | Number | Increments on every applied action or undo; clients send it as `expectedVersion` |
| `state` | Binary | Gzip-compressed JSON of the engine `GameState` (`game-engine.md` Section 6); contains the seed and hidden cards and is never returned to clients |
| `summary` | Map | Uncompressed copy of display fields: `score`, `moveCount`, `undoCount`, `completedRuns`, `stockDealsRemaining` |
| `startedAt`, `endedAt`, `lastActionAt` | String | ISO timestamps |
| `ttl` | Number | Only while the only seat is a guest's (Section 1, principle 10) |
| `entityVersion`, `createdAt`, `updatedAt` | | Section 1 |

Writes:

1. Each applied action or undo that leaves the session `IN_PROGRESS` is a single conditional `PutItem` (`version = :expected`). The compressed engine state for a Spider Solitaire game is under 8 KB.
2. Starting a session is one `TransactWriteItems`: the session (`attribute_not_exists(sessionId)`) and its seats.
3. Ending a session (`WON` or `ABANDONED`) is one `TransactWriteItems`: the session, conditioned on `version = :expected` and `status = IN_PROGRESS`; its seats with the new status; and each counted seat's `PlayerStats` item, conditioned on its own `version` (Section 8). Because the session condition fails once the session has ended, a game's result is counted exactly once, retries included.

Sample (state shown decoded; it is stored gzip-compressed):

```json
{
  "sessionId": "01JEX4Q8N6W2D3K5T7V9B1C3E5",
  "gameId": "spider-solitaire",
  "rulesSource": "CORE",
  "rulesVersion": 1,
  "engineSchemaVersion": 1,
  "options": { "suits": 1, "dealStyle": "MICROSOFT" },
  "variantKey": "dealStyle=MICROSOFT;suits=1",
  "seats": [{ "seatId": "S1", "playerId": "GUEST#us-east-1:4f1c2a9e-1d7b-4c55-9a0e-8f3f1d2b6c11" }],
  "status": "IN_PROGRESS",
  "version": 37,
  "state": "<gzip of GameState JSON, see game-engine.md Section 6>",
  "summary": {
    "score": 465,
    "moveCount": 33,
    "undoCount": 2,
    "completedRuns": 0,
    "stockDealsRemaining": 4
  },
  "startedAt": "2026-12-02T14:05:01.009Z",
  "lastActionAt": "2026-12-02T14:22:47.300Z",
  "entityVersion": 1,
  "createdAt": "2026-12-02T14:05:01.009Z",
  "updatedAt": "2026-12-02T14:22:47.300Z"
}
```

## 7. SeatAssignment

Table `AllPlay-SeatAssignments-<Stage>`. One item per player per session. This is the social layer: it answers "which sessions is this player in" without touching game state.

| Key | Attribute | Type |
|---|---|---|
| Partition key | `playerId` | String |
| Sort key | `sessionId` | String (ULID, so the partition sorts by start time) |

GSI `ByPlayerGame`:

| Key | Attribute | Format |
|---|---|---|
| Partition key | `playerGameKey` | `<playerId>|<gameId>` |
| Sort key | `statusSortKey` | `<status>#<sessionId>` |
| Projection | ALL | |

Access patterns:

| Pattern | Operation |
|---|---|
| Resume the player's current game of a given game (for example `/spider`) | Query `ByPlayerGame`, `playerGameKey = <playerId>|spider-solitaire`, `statusSortKey begins_with IN_PROGRESS#`, descending, limit 1 |
| List a player's sessions, newest first (merge, deletion, and later a history screen) | Query base table on `playerId`, descending |

Starting a session ends the player's in-progress session of the same game, so at most one seat per player and game is `IN_PROGRESS` and resume needs no ordering by activity. Whether the caller holds a seat is read from the session's own `seats` list, which the service loads anyway. The index is eventually consistent: a reload within milliseconds of starting a session can miss it, and then starts a new one.

A seat assignment is written twice: in the transaction that starts its session and in the transaction that ends it (Section 6). It is never written per move.

Attributes: `playerId`, `sessionId`, `gameId`, `seatId`, `status` (mirrors the session), `playerGameKey`, `statusSortKey`, `ttl` (guest seats only), plus Section 1 fields.

Sample:

```json
{
  "playerId": "GUEST#us-east-1:4f1c2a9e-1d7b-4c55-9a0e-8f3f1d2b6c11",
  "sessionId": "01JEX4Q8N6W2D3K5T7V9B1C3E5",
  "gameId": "spider-solitaire",
  "seatId": "S1",
  "status": "IN_PROGRESS",
  "playerGameKey": "GUEST#us-east-1:4f1c2a9e-1d7b-4c55-9a0e-8f3f1d2b6c11|spider-solitaire",
  "statusSortKey": "IN_PROGRESS#01JEX4Q8N6W2D3K5T7V9B1C3E5",
  "ttl": 1804515901,
  "entityVersion": 1,
  "createdAt": "2026-12-02T14:05:01.009Z",
  "updatedAt": "2026-12-02T14:05:01.009Z"
}
```

## 8. PlayerStats

Table `AllPlay-PlayerStats-<Stage>`. One item per player, game and variant. Updated when a session ends:

| Session end | Counted as |
|---|---|
| `WON` | A win |
| `ABANDONED` by the abandon route, or by starting a new game of the same game, with `moveCount` of at least 1 | A loss |
| `ABANDONED` with `moveCount` 0 | Not counted |
| `ABANDONED` by a merge that keeps another in-progress session (Section 9) | Not counted |

A game with no losing end condition, such as Spider Solitaire, records every loss as an abandon.

Computation, by a pure function in the game session service that folds one result into the current item (or into zeros when none exists):

| Attribute | Rule |
|---|---|
| `gamesPlayed`, `gamesWon`, `gamesLost` | Plus 1 to played and to won or lost |
| `bestScore` | Highest final `score` among wins; null before the first win |
| `fastestWinMoves` | Lowest final `moveCount` among wins; null before the first win |
| `currentWinStreak` | Plus 1 on a win, 0 on a loss |
| `longestWinStreak` | Highest `currentWinStreak` reached |
| `totalMoves` | Sum of final `moveCount` over counted games |
| `lastPlayedAt` | The session's `endedAt` |

The item carries an integer `version`. The folded item is written with `PutItem` conditioned on the version read (or `attribute_not_exists` for a first game), inside the transaction that ends the session (Section 6). A conflict on the stats item alone re-reads, re-folds and retries the transaction, up to three times. Win rate is computed by the client from `gamesWon / gamesPlayed`. Stats are derived data: account sessions never expire, so every item can be rebuilt from the player's ended sessions.

| Key | Attribute | Type |
|---|---|---|
| Partition key | `playerId` | String |
| Sort key | `statsKey` | `<gameId>#<variantKey>` |

No GSIs. The stats screen reads all of a player's stats with one `Query`, optionally with `begins_with(<gameId>#)`.

Attributes: `gameId`, `variantKey`, the attributes in the table above, `version`, `ttl` (guest items only), plus Section 1 fields.

Sample:

```json
{
  "playerId": "ACCT#7b3e9a10-5c2d-4f8e-a1b6-0d9c3e4f5a67",
  "statsKey": "spider-solitaire#dealStyle=MICROSOFT;suits=1",
  "gameId": "spider-solitaire",
  "variantKey": "dealStyle=MICROSOFT;suits=1",
  "gamesPlayed": 14,
  "gamesWon": 9,
  "gamesLost": 5,
  "bestScore": 1182,
  "fastestWinMoves": 104,
  "currentWinStreak": 3,
  "longestWinStreak": 4,
  "totalMoves": 1873,
  "lastPlayedAt": "2026-12-03T09:12:40.017Z",
  "version": 14,
  "entityVersion": 1,
  "createdAt": "2026-12-02T14:05:01.009Z",
```

## 9. MergeToken

Table `AllPlay-MergeTokens-<Stage>`. Proves that the account now signing in owned a guest identity. The client requests a token while still a guest, signs in, then redeems the token as the account (`authn-authz.md` Section 6).

| Key | Attribute | Type |
|---|---|---|
| Partition key | `tokenHash` | String: SHA-256 hex of the 32 byte random token; the raw token is returned to the client once and never stored |

Attributes: `sourcePlayerId` (the guest for a guest merge, or the account that issued it for account linking), `sourceKind` (`GUEST` or `ACCOUNT`), `status` (`ISSUED`, `REDEEMED`), `redeemedBy` (account `playerId`), `ttl` (issue time + 10 minutes), plus Section 1 fields. Redemption is a conditional update requiring an unexpired `ttl` and `status = ISSUED`, or `redeemedBy` equal to the redeeming account, so the client's retry of an interrupted merge (`authn-authz.md` Section 6, step 4) reaches the merge again. Expiry is in the condition because DynamoDB deletes expired items only eventually.

Sample:

```json
{
  "tokenHash": "c0a8d2f4e6b1...9e",
  "sourcePlayerId": "GUEST#us-east-1:4f1c2a9e-1d7b-4c55-9a0e-8f3f1d2b6c11",
  "sourceKind": "GUEST",
  "status": "REDEEMED",
  "redeemedBy": "ACCT#7b3e9a10-5c2d-4f8e-a1b6-0d9c3e4f5a67",
  "ttl": 1796225445,
  "entityVersion": 1,
  "createdAt": "2026-12-02T15:20:45.000Z",
  "updatedAt": "2026-12-02T15:21:30.000Z"
}
```

Merge semantics, executed by the merge service:

1. Every `SeatAssignment` of the guest moves to the account `playerId`: the matching `GameSession.seats[].playerId` is rewritten and the session loses its `ttl`, the account's seat is written without `ttl`, then the guest's seat is deleted. When both players hold an `IN_PROGRESS` session of the same game, the one with the later `lastActionAt` (else `startedAt`) stays in progress and the other ends `ABANDONED` without counting in `PlayerStats` (Section 8).
2. Each guest `Preference` scope is copied to the account only when the account has no item for that scope.
3. Each guest `PlayerStats` item is combined into the account's item for the same `statsKey`, and the guest item deleted, in one `TransactWriteItems` conditioned on the account item's `version`. Counters and `totalMoves` are summed; `bestScore` and `longestWinStreak` take the higher value, `fastestWinMoves` the lower; `currentWinStreak` and `lastPlayedAt` come from the item played more recently.
4. The guest `Player` item is set to `MERGED` with `mergedInto`; the account `Player` gains the guest id in `mergedGuestIds`.
5. The merge is idempotent: each step checks whether it already ran, so a retried merge produces the same result.

The merge service runs the data moves as an ordered list of steps: seats, preferences, stats, then players. A step interrupted part way leaves each item either moved or not yet moved, so a retry finishes it.

## 11. MetricRollup

Table `AllPlay-MetricRollups-<Stage>`. Daily aggregates read by the /admin metrics page.

| Key | Attribute | Type |
|---|---|---|
| Partition key | `rollupType` | `DAY` |
| Sort key | `period` | `yyyy-mm-dd` (UTC) |

The /admin page reads a date range with one `Query` (`period BETWEEN :from AND :to`).

Two writers fill each day's item:

1. Live counters. The decision and session services `ADD` to the current day's item as events happen: decision counts by outcome and failure class, LLM token totals, game starts, wins and abandons, and latency histogram buckets.
2. The daily rollup job. An EventBridge Scheduler rule runs at 00:15 UTC, scans `AllPlay-Players-<Stage>` once (projection: `kind`, `status`, `lastActiveAt`, `createdAt`) and writes `totalPlayers`, `totalAccounts`, `totalGuests`, `activePlayers30d`, `newPlayers` for the previous day. It then computes `p50` and `p95` latency from the histogram buckets.

Latency histogram bucket upper bounds (milliseconds): 250, 500, 750, 1000, 1500, 2000, 3000, 5000, and an overflow bucket. Two histograms are kept: `clientLatency` (end of speech to proposal shown, the "round trip for a move request" key metric) and `serverLatency`.

Sample:

```json
{
  "rollupType": "DAY",
```

## 12. GameDefinition

Table `AllPlay-GameDefinitions-<Stage>`, provisioned in the Game Building phase. Holds community-built rules documents in the same format as core rules documents (`game-engine.md` Section 4). Core games never live here.

| Key | Attribute | Type |
|---|---|---|
| Partition key | `gameId` | String, prefixed `community-` |
| Sort key | `version` | Number |

GSI `ByOwner`: partition `ownerPlayerId`, sort `updatedAt`, projection KEYS_ONLY plus `name`, `status`.
GSI `ByStatus`: partition `status`, sort `updatedAt`, projection KEYS_ONLY plus `name`, `ownerPlayerId` (lists `PUBLISHED` games).

Attributes: `gameId`, `version`, `name`, `ownerPlayerId`, `status` (`DRAFT`, `VALIDATING`, `PUBLISHED`, `REJECTED`), `sourceUrl`, `rulesDocument` (Map, the rules JSON), `validationReport` (Map), plus Section 1 fields.

## 13. Account Deletion

`DELETE /players/me` (`authn-authz.md` Section 8) removes the account's `Preference`, `SeatAssignment` and `PlayerStats` items, deletes every `GameSession` where the account holds the only seat, and deletes the Cognito user. Turn log events expire with their log group (`action-decision.md` Section 9.1). The `Player` item is written back as a minimal tombstone (`status = DELETED`, no email or name) so that daily rollups remain consistent.
